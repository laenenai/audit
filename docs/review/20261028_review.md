## How this review was produced

The review was run as a panel of five parallel reviewers, each covering one or two dimensions:

1. Go best practices, idiomatic Go, and code cleanliness.
2. Architecture, internal consistency, and long-term maintainability.
3. Security, threat model, and supply chain.
4. Testing and CI/build tooling.
5. Developer experience and documentation.

Each reviewer read the implementation, tests, documentation, and configuration, and returned findings with file:line evidence. The lead reviewer independently re-ran the toolchain gates, re-checked the critical claims against source, ran the CI task that the panel suspected was broken, inspected the dependency graph, and reproduced the PostgreSQL privilege behaviour in a disposable `pgvector/pgvector:pg18` container. Findings were deduplicated, cross-referenced, and assigned stable IDs, severities, breaking-change status, and effort estimates. Every finding below cites the current tree; the exact command output is in the appendix.

Backwards compatibility is explicitly **not** a constraint for this review. Several recommendations are marked breaking because the current design should change before outside adoption; those notes state the downstream impact rather than avoiding the change.

## Executive summary

**Verdict: No. This module is not production grade today.**

The core is better than most pre-1.0 libraries: the canonical encoding is carefully specified, the hash-chain verification logic is tested, the SQL is reviewed as SQL, the in-memory and Postgres adapters pass a substantial conformance suite, full tests and the race detector pass, and SQL injection was not found. The problem is not competence; it is that the guarantees advertised by the README and charter are either not enforced in the configurations the documentation offers, or are not implemented at all.

The five things that matter most:

1. **The append-only enforcement check can certify a role that can still rewrite history.** `CheckEnforcement` uses `pg_has_role(..., 'USAGE')`, while the application role is created `NOINHERIT`; a `NOINHERIT` member of the owner role has `USAGE=false` but can `SET ROLE` to the owner and `DELETE`. This was reproduced on PostgreSQL 18.6. The default single-DSN `Config.AppRole` mode is worse: the process retains owner credentials and only checks the narrowed role, directly contradicting the design record that rejected single-DSN `SET ROLE` as unsafe.
2. **The chain is not externally witnessed.** There is no checkpoint signing, publication, or persistence contract. The module detects accidental corruption and mutation by a role without write access, but a storage holder or compromised owner can rewrite the chain and recompute every digest; `Verify` with no trusted witness will accept it. Truncation of the tail is undetectable. Those limitations are documented, but they block the charter's “independently verified” claim and make retention unsafe.
3. **Transaction enlistment and tenant scope are invisible and unvalidated.** `WithTx` is context magic; an enlisted append skips role switching and tenant scoping, so a caller can append under owner credentials or as the wrong identity. Conversely, a verification through an unscoped transaction can see zero rows and report a non-empty chain as a valid empty chain.
4. **The CI gate can pass with a broken module.** The “detect Go packages” step suppresses `go list` errors and skips every real gate when the package list is empty. CI also has no `govulncheck`, no sqlc regeneration drift check, no `go mod tidy` check, and no coverage gate. At review time `govulncheck` exited 1 with four reachable vulnerabilities, all through the test-only testcontainers stack; the API-tooling migration fixed those dependencies and added the gate.
5. **Adoption and operations are unfinished.** There is no retention implementation, no query API, no metrics/tracing, no release workflow, no changelog, no threat model, and no contributor guide. Every process startup can reconcile roughly 960 partitions with savepoints. The docs are extensive but contradictory: the README and CONVENTIONS still require Go 1.25.6, the canonical-format doc says `0x02` while the constant is `0x01`, the linked Postgres design note says it is “not yet implemented” and “in-memory only”, and the old API compatibility task was broken.

## Findings

### 1. Go best practices and idiomatic Go

#### GO-01 — A witness equal to the verification root is falsely reported as `BreakTruncated`

**Severity:** MAJOR  
**Evidence:** `internal/eventlog/eventlog.go:360-370` starts the walk at `root.Sequence+1`; `internal/eventlog/eventlog.go:390-395` marks a witness as seen only when an entry at that sequence is pushed; `internal/eventlog/eventlog.go:410-414` then fails if the witness was never seen. The natural retention configuration is `VerifyOptions{Root: cp, Witness: cp}`.  
**Why it matters:** After retention removes everything through the checkpoint, no entry at that sequence is returned, so the walker reports `BreakTruncated` even though the root and witness agree. The workflow retention depends on looks exactly like tampering. The existing tests cover witness ahead of and behind the root, but not equal to it (`internal/eventlog/verify_test.go:480-510`).  
**Recommended change:** In `newWalker`, when `root.Sequence == witness.Sequence`, compare the digests: equal means the witness is already satisfied; unequal means `BreakCheckpointMismatch`. Add tests for equal/mismatched root-witness pairs, and for a witness immediately after the root.  
**Breaking change:** No; bug fix. Downstream retention verification stops producing false `BreakTruncated`.  
**Effort:** S

#### GO-02 — Layer-2 and layer-3 migration errors bypass the module's error taxonomy

**Severity:** MAJOR  
**Evidence:** `internal/migrate/migrate.go:195` returns `reconcile(...)` directly. `internal/migrate/partitions.go:105-107`, `:175`, and `:189` return raw `%w` errors from `CREATE TABLE`/`CREATE ROLE` operations. `internal/migrate/privileges.go:45` wraps every privilege statement error in `ErrInvalidConfig`, even when the cause is a lost connection, cancellation, or deadlock. Only the goose path and `ensureSchema` call `classify`. The package comment at `internal/migrate/migrate.go:335-336` promises that “nothing in this package returns a bare driver error across its boundary.”  
**Why it matters:** Callers cannot reliably branch with `errors.Is(err, domain.ErrInvalidConfig)` or `ErrUnavailable`. A transient database failure during partition creation reaches the caller as a raw `*pgconn.PgError`; a connection failure while applying privileges is mislabeled as a permanent configuration defect.  
**Recommended change:** Classify at the `reconcile` boundary (or in `ensurePartitions`/`execIdempotent`/`reconcilePrivileges`): context errors first, connection/lock/serialization failures as `ErrUnavailable`, DDL/schema failures as `ErrInvalidConfig`. Add a failure-injection test asserting one expected sentinel.  
**Breaking change:** Yes; error values change. Downstream callers that matched raw driver errors must update, but the documented contract becomes true.  
**Effort:** S

#### GO-03 — `classify` misclassifies context cancellation and depends on an untested goose error string

**Severity:** MAJOR  
**Evidence:** `internal/migrate/migrate.go:358-367` handles only `*pgconn.ConnectError` and `strings.Contains(err.Error(), "failed to acquire lock")`; everything else becomes `ErrInvalidConfig`. A canceled `provider.Up(ctx)` therefore matches `ErrInvalidConfig` even though `context.Canceled` remains in the chain. `internal/migrate/migrate.go:135-136` and `:348` refer to `WithLockTimeoutForTest` and `TestUp_LockTimeout_IsUnavailable`, but neither symbol exists anywhere in the repository.  
**Why it matters:** A canceled or timed-out migration is reported as “fix the deployment” rather than “retry/cancel”, and the only guard against goose rewording its unexported error text is the test that does not exist. An upgrade can silently turn a contended lock into a permanent defect classification.  
**Recommended change:** Check `errors.Is(err, context.Canceled)` and `context.DeadlineExceeded` before the default branch and preserve the context sentinel without adding `ErrInvalidConfig`. Add the promised test hook and a real contention test, or move to a typed goose sentinel.  
**Breaking change:** Yes; error classification changes. Downstream retry logic becomes correct.  
**Effort:** S

#### GO-04 — An enlisted append is not atomic; a failed head move can leave a committed entry

**Severity:** MAJOR  
**Evidence:** `internal/pglog/log.go:54-58` sends an enlisted append straight into the caller's transaction. `internal/pglog/log.go:235-257` performs `lockHead` → `insertEntry` → `moveHead` without a savepoint. `internal/pglog/log.go:315-329` makes `moveHead` a failure point when zero rows move.  
**Why it matters:** If the insert succeeds and `moveHead` fails, the event row is already in the caller's transaction. The caller owns commit/rollback; if it handles the error by continuing and committing, the log contains an entry the head does not acknowledge, and verification reports a head mismatch. A failed first append can also leave the head row created by `lockHead`. The “audit record and the thing it audits commit together or not at all” claim is only true if every caller rolls back on every append error.  
**Recommended change:** Wrap the enlisted `appendIn` in a savepoint and roll it back on any error, or explicitly document that an `Append` error poisons the caller's transaction and must be rolled back. The savepoint is preferable because it preserves the “failed append leaves no trace” property.  
**Breaking change:** No; strengthens the guarantee. Downstream callers that reused a transaction after a failed append no longer commit partial audit state.  
**Effort:** M

#### GO-05 — `Entries` narrows `uint64` to `int64` and does not cap page size

**Severity:** MAJOR  
**Evidence:** `internal/pglog/log.go:126-141` clamps only values below `FirstSequence`, then passes `FromSequence: int64(from)` with the comment “bounded by the caller's own page request.” That comment is false: `from` is never bounded by `math.MaxInt64`. The generated parameter is `int64` (`internal/pglog/gen/event.sql.go:26-30`), and `db/queries/event.sql:56-59` predicates `sequence >= @from_sequence`. `VerifyOptions.PageSize` is also unbounded (`internal/eventlog/eventlog.go:281-285`).  
**Why it matters:** `Entries(ctx, math.MaxUint64, n)` wraps to `-1`; the SQL predicate `sequence >= -1` returns the genesis entries instead of an empty page. This violates the `Log` contract and makes adapter behavior diverge (the memory adapter returns empty). A caller-controlled cursor or page size can force a full-chain scan and large allocation.  
**Recommended change:** Reject `from > math.MaxInt64` with `ErrInvalidArgument` (or clamp to `MaxInt64` to yield an empty valid page), remove the misleading `nolint` rationale, and enforce a maximum page size. Add conformance tests for `math.MaxUint64`, `math.MaxInt64+1`, and excessive limits.  
**Breaking change:** Yes only for currently invalid/absurd inputs; the contract becomes correct.  
**Effort:** S

#### GO-06 — The memory adapter checks cancellation only before taking the mutex

**Severity:** MINOR  
**Evidence:** `internal/eventlog/memory.go:70-81` checks `ctx.Err()` before `l.mu.Lock()`, then performs the append without checking again. `Head` and `Entries` follow the same pattern at `internal/eventlog/memory.go:100-108` and `113-125`. The conformance suite only tests a pre-canceled context (`audittest/suite.go:575-593`).  
**Why it matters:** A caller whose context is canceled while blocked on the mutex still appends after the lock is released, recording something for a request that has already gone away.  
**Recommended change:** Re-check `ctx.Err()` after acquiring the lock and before assigning a sequence or returning data. Add a test that holds the mutex, cancels the context, then releases it.  
**Breaking change:** No.  
**Effort:** S

#### GO-07 — `EntryDigest` allocates and copies the entire canonical encoding on every digest

**Severity:** MINOR  
**Evidence:** `internal/domain/chain.go:239-252` calls `h.Write(appendCanonical(nil, e))`. `appendCanonical` (`internal/domain/chain.go:259-274`) starts with a nil destination and appends every field, including `e.Detail`, into a fresh slice.  
**Why it matters:** Every append and every verification re-hash allocates and copies up to `MaxDetailLen` (64 KiB) per entry. A 1000-entry verification page can allocate tens of megabytes for encodings alone, on top of the stored detail bytes. The `defaultPageSize` comment at `internal/eventlog/eventlog.go:44-49` claims a page is “a few megabytes at the Detail size limit”, which is not true at 1000 × 64 KiB.  
**Recommended change:** Hash each length prefix and field incrementally, or write into a reusable/pre-sized buffer. Keep the encoding byte-identical and add a benchmark for append and verification.  
**Breaking change:** No; the digest must not change.  
**Effort:** S/M

#### GO-08 — `checkpointFrom` silently maps a corrupt `(sequence=0, digest≠0)` head to the empty checkpoint

**Severity:** MINOR  
**Evidence:** `internal/pglog/log.go:380-397` returns `domain.Checkpoint{}` whenever `sequence == 0`, without verifying that `digest` is the zero digest. No sanctioned write produces sequence 0 with a nonzero digest, and `Checkpoint.IsZero` requires both fields to be zero (`internal/domain/chain.go:347-349`).  
**Why it matters:** A corrupted or manually updated head row is reported as an empty chain, hiding storage corruption or an unexpected `UPDATE` by the application role.  
**Recommended change:** When `sequence == 0`, require the zero digest; otherwise return `ErrStorage` (or a dedicated corruption error). Add a test that corrupts the head row.  
**Breaking change:** No for valid data.  
**Effort:** S

#### GO-09 — Public entry points panic on nil or typed-nil inputs instead of returning typed errors

**Severity:** MAJOR  
**Evidence:** `audit.Verify` forwards to `eventlog.Verify` (`audit.go:171-172`), which dereferences `log` at `internal/eventlog/eventlog.go:289` with no nil check. `audit.Migrate` forwards to `migrate.Up` (`audit.go:224-225`), which calls `ensureSchema(ctx, pool)` and then `pool.Exec` at `internal/migrate/migrate.go:181,278-279`; a nil pool panics. `pglog.Open` checks `cfg.DB == nil` (`internal/pglog/pglog.go:199-201`) but a typed-nil `(*pgxpool.Pool)(nil)` in the `DB` interface passes. `txFromContext` (`internal/pglog/pglog.go:272-274`) can return a typed-nil `pgx.Tx`, which `appendIn` then calls.  
**Why it matters:** A dynamically assembled configuration or a nil transaction crashes the process instead of returning `ErrInvalidConfig`/`ErrInvalidArgument`. For a library embedded in a service, a panic is a denial-of-service path.  
**Recommended change:** Add explicit nil checks to `Verify`, `Migrate`, `Status`, and the transaction path; detect typed nils for interface values; add table tests for nil and typed-nil inputs.  
**Breaking change:** Yes for nil inputs that currently panic; now they return errors.  
**Effort:** S

#### GO-10 — Negative `VerifyOptions.PageSize` silently means the default, while `Entries` rejects non-positive limits

**Severity:** NIT  
**Evidence:** `internal/eventlog/eventlog.go:281-285` treats every value `<= 0` as `defaultPageSize`. `internal/eventlog/memory.go:117-119` and `internal/pglog/log.go:123-125` reject `limit <= 0` with `ErrInvalidArgument`. The `VerifyOptions.PageSize` doc says “Zero means defaultPageSize” but does not define negative values.  
**Why it matters:** Two public APIs disagree about whether a non-positive page size is invalid. A caller passing `-1` gets a silent default in one path and an error in another.  
**Recommended change:** Treat negative page sizes as `ErrInvalidArgument` in `Verify` and `VerifyEntries`, or document the clamping consistently. Add a test.  
**Breaking change:** Yes for negative values; low impact.  
**Effort:** S

### 2. Code cleanliness

#### CLN-01 — The security-relevant `isPlainIdentifier` predicate is duplicated with no drift test

**Severity:** MINOR  
**Evidence:** `internal/migrate/config.go:145-159` and `internal/pglog/pglog.go:368-382` are identical implementations. Both guard values interpolated into SQL: `SET LOCAL ROLE` (`internal/pglog/log.go:224`) and `GRANT`/`REVOKE` (`internal/migrate/privileges.go:68-98`). `internal/pglog/pglog.go:358-366` says the duplication is checked “for the same reason the table names are”, but `internal/pglog/pglog_test.go:671-693` compares only the schema constants, not the predicates.  
**Why it matters:** A future edit that loosens one copy (for example, allowing `$`, `.`, or a leading digit) silently weakens the other. `pgx.Identifier.Sanitize` remains a second layer, but the predicate is described as deliberate and has no test holding the copies together.  
**Recommended change:** Move the predicate to one small internal package and use it from both packages, or add an exhaustive table-driven test comparing both implementations. Keep `Sanitize` as the second layer.  
**Breaking change:** No.  
**Effort:** S

#### CLN-02 — The canonical-format documentation says version `0x02`, but the constant is `0x01`

**Severity:** MAJOR  
**Evidence:** `internal/domain/chain.go:22` says “canonicalVersion 1 byte, currently 0x02”. `internal/domain/chain.go:121` declares `const canonicalVersion byte = 0x01`. `internal/domain/chain.go:69-71` says the version history is “**0x01**, tag `audit:entry:v1`. That is the whole history.”  
**Why it matters:** This is the byte that selects the persistence format. A maintainer trusting the encoding specification at line 22 could change the constant to `0x02`, silently invalidating every stored digest. Cryptographic format documentation must be exact.  
**Recommended change:** Correct the specification to `0x01` and add a test that asserts the literal against the documented byte, alongside the existing domain-tag pin test.  
**Breaking change:** No; documentation fix.  
**Effort:** S

#### CLN-03 — Comments and package docs describe a different, older API

**Severity:** MINOR  
**Evidence:** `internal/eventlog/eventlog.go:9-10` says “the Postgres one a later increment adds” although `internal/pglog` exists. `internal/eventlog/eventlog.go:82-91` says “no transactional adapter yet” and “This increment ships neither” although `pglog.WithTx` exists. `internal/eventlog/eventlog.go:325` says entries must begin at the chain's genesis, while `VerifyOptions.Root` explicitly supports a suffix. `audittest/suite.go:34-36` says the facade re-exports no verification functions and waits for the increment that adds `Open`, but `audit.go:159-181` exports `Verify`, `VerifyEntries`, `FirstSequence`, and `audit.go:201` exports `Open`.  
**Why it matters:** The conformance suite and port docs are the consumer-facing contract. Stale rationale teaches reviewers and adopters the wrong API and undermines trust in the otherwise careful documentation.  
**Recommended change:** Rewrite these paragraphs in the present tense, remove “later increment” language, and add a grep-based docs check for stale phrases.  
**Breaking change:** No.  
**Effort:** S

#### CLN-04 — `RunLogSuite` is a single ~500-line function

**Severity:** NIT  
**Evidence:** `audittest/suite.go:76` starts `RunLogSuite`; the function runs to approximately line 595 and contains every subtest inline, from empty-log behavior through concurrency and error-leak invariants. Helpers exist below it, but the main function is still a very long read.  
**Why it matters:** The suite is the contractual artifact consumers run; a 500-line function makes it harder to review, extend, and identify which invariant a failure belongs to.  
**Recommended change:** Split subtest bodies into package-level helper functions (`runEmptyLog`, `runPaging`, `runTamper`, `runConcurrency`, `runErrorLeak`) and keep `RunLogSuite` as the ordered registration list.  
**Breaking change:** No.  
**Effort:** S

### 3. Architecture and internal consistency

#### ARCH-01 — The root facade forces the Postgres and migration stack on every consumer, including memory-only users

**Severity:** MAJOR  
**Evidence:** `audit.go:31-37` imports `pgx`, `pgxpool`, `internal/migrate`, and `internal/pglog`; `audit.go:55` aliases `Config = pglog.Config`; `audit.go:224` takes `*pgxpool.Pool`; `audit.go:244` takes `pgx.Tx`. `go list -deps .` expands to 245 packages including `github.com/jackc/pgx/v5`, `pgxpool`, `database/sql`, and `github.com/pressly/goose/v3`. The comment at `internal/pglog/pglog.go:83-89` says the schema constant is duplicated so consumers that only open a log “should not link a migration engine”, but the root imports `internal/migrate` unconditionally.  
**Why it matters:** A consumer that only wants `audit.NewMemory` or the `Log` port still compiles and links the PostgreSQL driver, pgxpool, goose, and `database/sql`, inherits their version constraints and vulnerability surface, and cannot use the chain/port independently of the database adapter. The “one import” facade is syntactically simple but architecturally backwards: the root depends on every adapter.  
**Recommended change:** Move `Open`, `Migrate`, `WithTx`, `DB`, `Config`, `Enforcement`, and `MigrateConfig` into a public `github.com/laenenai/audit/postgres` package or a separate Go module. Keep the root for domain types, the `Log` port, `NewMemory`, and verification. Move pgx/goose/testcontainers out of the root module graph.  
**Breaking change:** Yes. Downstream consumers of `audit.Open`/`audit.Migrate`/`audit.WithTx`/`audit.Config` must change imports; memory-only consumers stop linking the database stack.  
**Effort:** M

#### ARCH-02 — `Verify` reads the head after walking, so a live log can be reported as tampered

**Severity:** MAJOR  
**Evidence:** `internal/eventlog/eventlog.go:288-318` pages through entries and only then calls `log.Head`, requiring exact equality. `internal/pglog/log.go:170-184` documents that each unenlisted read is its own transaction and only a caller-supplied `REPEATABLE READ` transaction gives one snapshot. The only stable-verification test explicitly enlists a snapshot (`internal/pglog/pglog_test.go:750-799`); the test comment at `:738-749` admits the unenlisted half is “deliberately not asserted to fail.”  
**Why it matters:** A normal periodic verifier or health check that runs while appends are landing can see a new append after the walk and return `BreakHeadMismatch`, which is `ErrChainBroken`. A healthy log is reported as tampered; operators either trigger a false incident or learn to ignore the one error that matters. The in-memory adapter has no snapshot equivalent.  
**Recommended change:** Capture a target checkpoint at the start and verify exactly to it, or add `VerifyOptions.Target`/`Snapshot` and a pglog helper that opens the snapshot transaction. Document that default verification is for a quiescent chain. Consider making the target behavior the default and the strict “head must be current” behavior opt-in.  
**Breaking change:** Additive option: no. Changing the default result: yes; downstream verifiers become stable, while callers that want an exact-current assertion opt in.  
**Effort:** M

#### ARCH-03 — `Verify` does not check the chain identity the caller asked for

**Severity:** MAJOR  
**Evidence:** `VerifyOptions` (`internal/eventlog/eventlog.go:141-188`) has `Root`, `Witness`, and `PageSize` but no expected `ChainID`. `walker.push` (`internal/eventlog/eventlog.go:379-401`) checks sequence, predecessor, digest, and witness, but never compares `Event.Chain`. The `Log` interface (`internal/eventlog/eventlog.go:101-139`) exposes no chain identity. `VerifyEntries` (`internal/eventlog/eventlog.go:330-338`) accepts any chain. The splice test only replaces one entry and builds both chains with the same `ChainID` (`internal/eventlog/verify_test.go:184-193`).  
**Why it matters:** A shared store holds many chains. A query bug, an adapter bound to the wrong chain, or an exported file from another tenant can return an internally consistent foreign chain and `Verify` will accept it. The digest commits to `ChainID`, but the verifier has no expected value to compare, so the chain binding is not actually enforced.  
**Recommended change:** Add `VerifyOptions.Chain domain.ChainID` (or a `Log.Chain() ChainID` method) and reject entries whose `Event.Chain` differs. Include the chain ID in any checkpoint encoding/publication. Add a test that exports a complete valid chain from another chain and requires failure.  
**Breaking change:** No with a new option; yes if `Log` gains a method. Downstream adapters and callers gain explicit tenant/chain binding.  
**Effort:** S

### 4. Security

#### SEC-01 — `CheckEnforcement` misses privileges reachable through `SET ROLE`, so it can certify an unsafe application role

**Severity:** BLOCKER  
**Evidence:** `internal/pglog/enforcement.go:101-106` uses `pg_has_role(s.name, r.oid, 'USAGE')` for superuser/BYPASSRLS and `pg_has_role(s.name, c.relowner, 'USAGE')` for ownership, then `has_table_privilege` for UPDATE/DELETE/TRUNCATE. `internal/migrate/privileges.go:119-127` creates the application role `NOINHERIT`. On PostgreSQL 18.6, a `NOINHERIT` role granted membership in an owner role returned `USAGE=false`, `MEMBER=true`, `SET=true`; `has_table_privilege(app, t, 'DELETE')` was false, yet `SET ROLE owner` followed by `DELETE` succeeded. A `NOINHERIT` member of a superuser role returned the same `USAGE=false`/`MEMBER=true`/`SET=true` triple. `canAssumeRole` at `internal/pglog/pglog.go:282-291` uses `MEMBER` rather than `USAGE`, so the distinction is already present elsewhere.  
**Why it matters:** A deployment that grants the application role membership in the owner, superuser, BYPASSRLS, or any group holding mutating privileges can be reported `AppendOnly: true`, so `RequireAppendOnlyEnforcement` accepts it. A compromised application then executes `SET ROLE` and rewrites or truncates history. This is a false security guarantee, which is worse than no check.

#### SEC-02 — The documented single-DSN `Config.AppRole` mode retains owner credentials and checks only the narrowed role

#### SEC-03 — `WithTx` can run under owner credentials and skips tenant scope

#### SEC-05 — The hash chain is unsigned and no checkpoints are published; a storage holder can rewrite everything

**Severity:** BLOCKER  
**Evidence:** `README.md:6-8` and `CHARTER.md:3` claim independent verifiability, but `README.md:10-14` says checkpoint signing and publication are not built, and `README.md:64-71` says a root read back out of the same storage “proves nothing.” `internal/domain/chain.go:340-345` stores only `Sequence` and `Digest`; `internal/eventlog/eventlog.go:144-181` accepts `Root` and `Witness` from the caller. #### SEC-07 — RLS tenant scope is a caller-settable GUC, not an authorization boundary

**Severity:** MAJOR

### 7. Long-term maintainability

#### MAINT-01 — Every process startup can reconcile roughly 960 partitions, one savepoint per table

**Severity:** MAJOR  
**Evidence:** `internal/migrate/migrate.go:175-196` always runs goose `Up` and `reconcile`. `internal/migrate/partitions.go:120-137` loops over every hash partition and every month; defaults are 64 hash partitions, 1 month behind, and 12 ahead (`internal/migrate/config.go:17-31`), yielding 14 monthly partitions plus one default per hash partition: 64 × 15 = 960 leaf tables. `internal/migrate/partitions.go:234-251` opens a nested transaction/savepoint for every `CREATE TABLE IF NOT EXISTS`. ## Cross-cutting themes

1. **Claims outrun mechanisms.** The README says “independently verified” while checkpoint publication is absent; it offers a single-DSN `AppRole` mode while the design record says that mode weakens the guarantee; the schema calls the RLS policy “tenant isolation” while the tenant is a caller-settable GUC. The clearest documentation is often the most dangerous, because it tells an adopter which guarantees to rely on.
2. **Enforcement checks the happy path, not the actual privilege graph.** `CheckEnforcement` checks one table, one trigger name, and one inheritance mode. It does not follow `SET ROLE`, column grants, schema ownership, disabled triggers, or the head table. The same pattern appears in `ensureRole`, which assumes a role it did not create has the attributes it would have set.
3. **Security-relevant state is invisible at the API boundary.** `WithTx` hides the transaction in a context; enlisted appends skip role and tenant scoping; `Verify` has no expected chain identity; a wrong tenant scope produces a successful empty verification. The Go type system is not carrying the invariants the docs describe.
4. **Verification semantics are underspecified at the edges.** The core walk is sound, but root-equals-witness, live-log head reads, foreign chains, negative page sizes, corrupt head rows, and checkpoint persistence are all edge cases with either a wrong result or no test.
5. **Tooling and docs drift in the same direction: away from the code.** Go 1.25.6 in README/CONVENTIONS, `0x02` in the canonical-format doc, “later increment” comments after the increment shipped, a design note that says “in-memory only”, and an API compatibility task that could not run. The repository has strong prose discipline but no mechanical check that prose matches code.
6. **The operational lifecycle is missing.** No retention job, no checkpoint publication, no query API, no metrics/tracing, no release workflow, no changelog. The code is a durable append path; it is not yet a production audit system.
7. **Tests are strong where they exist and absent at the contract boundaries.** The domain, eventlog, pglog, and migrate tests are serious work; 81.0% union coverage and a green race run are real. But the facade is 0% covered, the conformance suite is never tested against a broken adapter, and the adversarial paths (cancellation under contention, malformed rows, commit failure, overflow) are not exercised.
8. **Duplication is mostly deliberate but under-checked.** Schema constants and `isPlainIdentifier` are duplicated to keep goose out of pglog; only the schema constants are drift-tested. The duplication is defensible, but the security predicate needs the same protection.

## Open questions for the maintainer

### Q1 — What is the v1 security guarantee: tamper-evidence against the storage holder, or only internal consistency plus a caller-supplied witness?

**Context:** The README and CHARTER say “independently verified”, but there is no signed checkpoint or publication mechanism. Without an external witness, a storage holder can rewrite the chain and recompute every digest, and a truncated tail verifies clean. The README admits this, but the top-line claim still implies a stronger guarantee. The answer decides whether SEC-05 is a v1 feature or a scope cut.

**Why it blocks or shapes work:** It determines the design of `Verify`, the retention API, the persistence contract for checkpoints, whether a trusted witness becomes mandatory, and what an outside adopter can rely on.

**Options:**
1. **Implement signed checkpoints and publication in v1** (OpenBao transit or equivalent, write-once storage), and make `Verify` require or explicitly label the absence of a trusted checkpoint. Recommended if the module is sold as tamper-evident.
2. **Ship only caller-supplied witnesses** and narrow the claim to “tamper-evident against a role without write access; the caller must supply an external witness.” Cheaper, but the module does not by itself deliver the charter promise.
3. **Drop tamper-evidence language** and position the module as an append-only, hash-linked audit store. Simplest, but it gives up the differentiator.

**Recommendation:** Option 1 for a production-grade audit module; if schedule forces option 2, make the limitation impossible to miss in the README, SECURITY, and `Verify` docs, and remove retention claims that depend on a published root.

### Q2 — Is the deployment model two pools only, or is single-DSN `Config.AppRole` a supported mode?

**Context:** `docs/superpowers/specs/2026-10-23-postgres-backend-notes.md:151-167` records the decision “two pools, not two session states” and explicitly rejects single-DSN `SET ROLE` as weakening the guarantee. The code and README still support `Config.AppRole` and describe it as keeping privilege separation. `CheckEnforcement` checks only the narrowed role, so the owner credential in the process is never assessed.

**Why it blocks or shapes work:** It decides whether SEC-02 is a removal, a safety gate, or a documentation change, and it changes `Open`, `Migrate`, `CheckEnforcement`, the README, and many tests.

**Options:**
1. **Require a runtime application-role pool; remove `AppRole` from production** (optionally keep a development-only `AllowUnsafeSingleDSN` with no enforcement claim). Recommended.
2. **Keep single-DSN but check both the connected role and the target role**, and fail `Open` when the connected credential can mutate history. This preserves convenience and makes the risk explicit.
3. **Keep the current mode and document it as non-enforcing.** Cheapest, but it contradicts the design record and invites the false guarantee.

**Recommendation:** Option 1. If option 2 is chosen, never report `AppendOnly: true` for the owner-connected handle and make the residual risk explicit in the startup log and README.

### Q3 — Is RLS an authorization boundary or an accidental-omission guard?

**Context:** `app.tenant_id` is a caller-settable GUC. Any role can set it to another tenant, so RLS does not prevent a compromised application from reading another tenant's history. The README says read authorization belongs to IAM, but the schema, tests, and migration comments present the policy as tenant isolation.

**Why it blocks or shapes work:** If RLS is an authorization boundary, the module needs per-tenant roles or a security-definer derivation; if it is not, the docs and tests must say so and the threat model must rely on IAM for tenant authorization.

**Options:**
1. **Make tenant scope structural** with per-tenant database roles or a security-definer function that derives the tenant from the authenticated role. Strongest, but a significant operational and API change.
2. **Keep the GUC and document RLS as an accidental-omission guard**, not an authorization boundary; move tenant authorization wholly to IAM. Recommended if the module's charter already delegates read authorization.
3. **Keep the GUC and require a trusted connection wrapper** that validates the tenant before every transaction. Weaker than option 1 and easy to bypass.

**Recommendation:** Option 2 unless a consumer explicitly requires database-enforced tenant isolation. Remove or qualify the “tenant isolation” wording either way.

### Q4 — Who owns retention: the module, the operator, or no one in v1?

**Context:** Retention is not implemented. The schema's default partition silently absorbs rows when the monthly window is behind, and those rows cannot be dropped by a partition-drop retention job. The design note says retention and checkpoint publication are inseparable. The module currently offers `VerifyOptions.Root` but no tool to produce, schedule, or consume a retention boundary.

**Why it blocks or shapes work:** It decides whether MAINT-02 is a module feature, an operator runbook, or a documented non-goal, and it determines whether SEC-05 is on the critical path.

**Options:**
1. **Module ships a retention/partition-maintenance job or CLI** that drops whole partitions at a published checkpoint boundary and moves default-partition rows. Recommended for an adoptable module.
2. **Module ships the SQL primitives and a documented runbook**, leaving scheduling to the operator. Less code, more operational burden.
3. **Defer retention entirely** and document that the log grows without bound; remove the retention claims from the README. Cheapest, but not production-ready for audit volumes.

**Recommendation:** Option 1, paired with Q1. If deferred, remove retention from the charter/README and add a capacity warning.

### Q5 — What query API belongs in v1?

**Context:** The schema ships indexes for actor, subject, time, and event ID, but the public port exposes only `Append`, `Head`, and `Entries`. `README.md:86-87` says the query API is not built. Consumers must write raw SQL to answer ordinary audit questions, duplicating tenant scoping and error mapping.

**Why it blocks or shapes work:** It affects the public surface, the API compatibility contract, the package layout (ARCH-01), and whether the existing indexes are justified.

**Options:**
1. **Add a small read-only query port** with explicit filters (chain, actor, subject, action, time range, event ID), pagination, and the same tenant binding as the log. Recommended.
2. **Keep raw SQL as the supported path** and document the schema and safety rules. Less code, but consumers may bypass the contract.
3. **Remove the unused indexes** and explicitly declare querying out of scope for v1. Simplest, but weakens adoption.

**Recommendation:** Option 1, limited to the filters the existing indexes support; keep verification on the chain and queries on the indexes.

### Q6 — Should transaction participation stay context-based, or become a typed API?

**Context:** `WithTx(ctx, tx)` hides the transaction in a context. A caller who forgets it gets a standalone append that commits independently; a caller who supplies an owner/scoped-wrong transaction writes under the wrong identity. The type system cannot tell either case. `Append` also does not use a savepoint, so a partial enlisted append can survive if the caller commits after an error.

**Why it blocks or shapes work:** It determines whether SEC-03/SEC-04 and GO-04 are fixed by validation, a helper, or a new API. It also changes the README and every downstream call site.

**Options:**
1. **Add a typed transaction API** (`AppendTx(ctx, tx, rec)`, `LogForTx(tx)`, or a `Transaction` type) and deprecate context enlistment. Recommended; makes atomicity visible and allows savepoint/role/tenant validation.
2. **Keep `WithTx` but validate the transaction** (current_user, tenant GUC) and use a savepoint. Smaller change, but enlistment remains invisible.
3. **Keep both**: typed API as the recommended path, context as a convenience with validation and documentation.

**Recommendation:** Option 1 or 3. The audit-atomicity property is too important for an invisible context convention.

### Q7 — What should `Verify` do when the log is live?

**Context:** `Verify` pages through entries and then reads `Head`; a concurrent append between the two makes it report `BreakHeadMismatch`, which is `ErrChainBroken`. The only safe path is a caller-supplied REPEATABLE READ transaction, which is documented only in `pglog.reader`, not on `Verify`. The memory adapter has no snapshot equivalent.

**Why it blocks or shapes work:** It decides whether ARCH-02 is a default-behavior change, a new option, or a documentation-only warning, and it affects every health check and periodic verifier.

**Options:**
1. **Verify to a target checkpoint captured at the start** (or an explicit `Target` option) so later appends are ignored. Recommended; stable and matches “verify this prefix”.
2. **Require a snapshot transaction** for live verification and return a distinct transient result when the head moves. Precise, but awkward for the memory adapter.
3. **Document that `Verify` requires a quiescent chain** and leave the current strict behavior. Cheapest, but invites false tamper alarms.

**Recommendation:** Option 1, with an explicit strict mode for callers that need “head must be current”.

### Q8 — What is the supported PostgreSQL and platform matrix?

**Context:** The README says Postgres 17+, the tests use `pgvector/pgvector:pg18`, and the panel reproduced behaviour on PostgreSQL 18.6. No test runs against 17, a managed service, or a different OS. The partition/RLS/trigger features used are not obviously 18-only, but that is not verified.

**Why it blocks or shapes work:** It affects CI (CI-04), the migration/DDL, documentation, and the support burden for adopters on managed Postgres.

**Options:**
1. **Support PostgreSQL 17 and 18** and add a CI matrix for both (and a `GOOS` build matrix). Recommended.
2. **Support PostgreSQL 18 only** and state it clearly; simpler test matrix, narrower adoption.
3. **Declare “tested on 18.6” without a support promise**; acceptable only if the README is explicit and the risk is owned upstream.

**Recommendation:** Option 1 if adoption is the goal; at minimum, test the exact minimum version claimed.

### Q9 — Should the Postgres adapter remain in the root module?

**Context:** The root facade imports pgx, pgxpool, goose, and `database/sql`, so a memory-only consumer still links the entire database stack. `internal/pglog` duplicates the schema constant specifically to avoid linking goose, but the root imports `internal/migrate` anyway. The `go list -deps .` graph is 245 packages.

**Why it blocks or shapes work:** It determines the public import paths, the compatibility surface, the release cadence, and whether consumers can use the chain/port independently. It is a breaking change, so it should happen before outside adoption.

**Options:**
1. **Split `audit/postgres` (or a separate Go module)** for `Open`, `Migrate`, `WithTx`, `DB`, `Config`, `Enforcement`, and `MigrateConfig`; keep the root dependency-free. Recommended.
2. **Keep the single facade** and accept the dependency weight; simpler for consumers, worse for memory-only users and supply-chain review.
3. **Keep the facade but isolate the Postgres adapter behind a build tag/subpackage**; good for binaries, awkward for documentation and testing.

**Recommendation:** Option 1. It pairs naturally with the public-type visibility fix (DX-03).

### Q10 — What is the public API and versioning policy for the post-1.0 surface?

**Context:** An API compatibility gate is necessary, but the facade currently hides useful constructors/parsers while exposing aliases that godoc cannot document. `Status`, `Applied`, `NewFixedClock`, `ParseDigest`, `ParseEventID`, and `CanonicalTime` are internal-only despite being described as caller-facing. Tags exist, but there was no changelog or deprecation policy; `CHANGELOG.md` and `UPGRADING.md` were added in the API-tooling migration.

**Why it blocks or shapes work:** It determines which symbols move to public packages, how the compatibility surface is maintained, and what downstream consumers can rely on across releases.

**Options:**
1. **Publish a minimal but complete operational surface** (the missing constructors/parsers/status) and a written pre-1.0/1.0 policy with deprecation rules. Recommended.
2. **Keep the surface minimal** and document that operational APIs are internal; consumers use raw SQL/their own tooling. Cheaper, but reduces adoption.
3. **Publish everything internal as aliases**; maximal reachability, but expands the compatibility burden and godoc noise.

**Recommendation:** Option 1. Decide explicitly; do not let the compatibility surface include internal symbols that consumers cannot call.

### Q11 — What observability contract should the module offer?

**Context:** There are no metrics, traces, or operational logs. `Config.Logger` is used only by `Open`; append/verify/retention have no hooks. `.golangci.yml` has a dead depguard rule for an `internal/obs` package that does not exist.

**Why it blocks or shapes work:** It decides whether consumers wrap every call, whether the module takes an OTel dependency, and what production dashboards can rely on.

**Options:**
1. **Add a small optional observer/hooks interface** with a no-op default (append/verify durations and errors, checkpoint age, partition backlog). Recommended; no OTel dependency in the core.
2. **Adopt OpenTelemetry directly** and emit metrics/traces from the adapter. More power, more dependency weight and configuration.
3. **Leave observability to consumers** and remove the dead lint rule. Cheapest, but every adopter reinvents it.

**Recommendation:** Option 1, with an optional OTel adapter in a separate package if needed.

### Q12 — Should testcontainers remain in the production module graph?

**Context:** `github.com/testcontainers/testcontainers-go/modules/postgres` is a direct `go.mod` dependency because `internal/testdb` is a normal package imported only by tests. It pulls in moby/docker/x/crypto/x/text and accounts for all four current govulncheck findings. It is not linked into consumers' binaries, but it is part of the module graph and every scanner's view.

**Why it blocks or shapes work:** It determines whether SEC-11/CI-03 can be satisfied cleanly and whether external consumers inherit the test stack's dependency constraints.

**Options:**
1. **Move the test harness into a separate test module** (with a workspace or local replace) so the root `go.mod` contains only pgx/goose. Recommended.
2. **Keep it and add a documented govulncheck scope** that excludes test-only packages. Less restructuring, but scanners still see it.
3. **Replace testcontainers with a simpler harness** using `TEST_DATABASE_URL` only. Lightest dependency, but loses the self-contained test path.

**Recommendation:** Option 1; it is the cleanest way to keep the production module small while preserving the container-backed suite.

## Assumptions and unverified items

- **Backwards compatibility is not a constraint.** The review assumes the charter's adoption table is accurate: `cas` is greenfield, and `kgs`/`acre` have no production use yet. Breaking changes are therefore acceptable; downstream impact is noted per finding but was not tested against real consumers.
- **Reviewed state.** The review covers `main` at `e4eff0c` plus the authoritative uncommitted toolchain bump. The superseded `chore/publication-readiness` branch was not reviewed. The working tree was not reset or cleaned.
- **Toolchain.** All gates were run on Go 1.27.3 on Linux/amd64. The review did not run on other Go patch releases, macOS, Windows, or architectures; the cgo-free build was verified only on Linux.
- **PostgreSQL.** Integration tests and the privilege experiment used `pgvector/pgvector:pg18` (PostgreSQL 18.6) in Docker. The README claims Postgres 17+; version 17 and managed Postgres services were not tested. The pgvector extension is not used by this module; the image is a cross-module convention.
- **Docker/testcontainers.** Docker was available and the full container-backed suite ran. The review did not audit the testcontainers/moby implementation beyond `govulncheck`; the four CVEs are test-only reachability as reported by the tool.
- **Security scope.** This was a code and configuration review plus a targeted privilege experiment, not an external penetration test or cryptographic audit. The canonical encoding was reviewed for injectivity and domain separation, not formally proven.
- **Remote repository state.** Local tags and branches were inspected. GitHub branch protection, required checks, remote tags, release settings, and the actual default branch configuration were not verified.
- **Coverage numbers.** Default per-package coverage was 47.9% total, with root/audittest/testdb at 0.0%. With `-coverpkg=./...`, the union total is 81.0%; the root package remains 0.0%. The 0.0% figures for `audittest`/`testdb` under default instrumentation partly reflect how Go instruments imported packages, not necessarily dead code; `testdb` functions show 75-80% when instrumented through importing tests.
- **Dependency licences and provenance.** Licences of transitive dependencies were not reviewed; no SBOM or signed release exists to verify.
- **No current sqlc/tidy drift.** `sqlc diff`, `go mod tidy -diff`, and `go mod verify` all exited 0 at review time; the finding is that CI does not enforce them, not that the tree is currently drifted.
- **No SQL injection found.** The review checked every dynamic identifier path and found `Sanitize` plus `isPlainIdentifier`; it did not attempt a full taint analysis of every pgx call.
